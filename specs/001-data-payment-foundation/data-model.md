# Phase 1 Data Model: Data & Payment Foundation

Derived from spec Key Entities, Functional Requirements, and Phase 0 research. This is the
authoritative shape of the `orders` record of truth.

## Entity: Order

The authoritative record of a single purchase of the single product.

| Field | Type (DB) | Null? | Default | Rules / Source |
|-------|-----------|-------|---------|----------------|
| `id` | `uuid` | no | `gen_random_uuid()` | Primary key; stable identity independent of any provider reference (FR-003). |
| `email` | `text` | yes¹ | — | Customer contact email. Required at creation via Zod (FR-009); nullable so PII can be anonymized later (FR-013, D9). |
| `whatsapp` | `text` | yes¹ | — | Customer WhatsApp number. Same required-at-creation / nullable-for-erasure rule as `email`. |
| `amount` | `bigint` | no | — | Payment amount in the currency's **smallest unit** (e.g. cents). `CHECK (amount >= 0)` (FR-011, D5). |
| `currency` | `text` | no | — | ISO-4217 code. `CHECK (char_length(currency) = 3)`, stored uppercase. |
| `payment_status` | `text` | no | `'pending'` | `CHECK (payment_status IN ('pending','success','failed','refunded'))` (FR-004, D6). |
| `fulfilled` | `boolean` | no | `false` | Business fulfillment flag, independent of payment status (FR-005). |
| `stripe_payment_intent_id` | `text` | yes | — | Provider payment reference. Partial **unique** index where not null (FR-007, D7). Null until an intent is created. |
| `stripe_receipt_url` | `text` | yes | — | Provider receipt reference (FR-002). |
| `stripe_customer_id` | `text` | yes | — | Optional provider customer reference (FR-002). |
| `notes` | `text` | yes | — | Free-form internal notes; editable without touching payment/fulfillment (FR-012). |
| `created_at` | `timestamptz` | no | `now()` | Set once (FR-008). |
| `updated_at` | `timestamptz` | no | `now()` | Advanced on every update via trigger (FR-008). |

¹ Enforced as **required at creation** by the Zod create schema / DAL; the column is nullable
only to permit later PII anonymization while retaining the financial record.

### Table-level constraints

- `PRIMARY KEY (id)`
- `CHECK (amount >= 0)`
- `CHECK (char_length(currency) = 3)`
- `CHECK (payment_status IN ('pending','success','failed','refunded'))`
- **`CHECK (NOT fulfilled OR payment_status = 'success')`** — fulfillment only on a paid order (FR-006, SC-005, D8).
- **Partial unique index**: `orders_payment_intent_uidx` on `stripe_payment_intent_id` where not null — declared in Drizzle as `uniqueIndex('orders_payment_intent_uidx').on(t.stripePaymentIntentId).where(sql\`${t.stripePaymentIntentId} is not null\`)` (FR-007, D7).
- Lookup index: `orders_created_at_idx` on `created_at DESC` (for later dashboard listing; cheap to add now).
- `updated_at` maintained at the ORM layer via Drizzle `$onUpdate(() => new Date())` (no DB trigger; D3).
- **Row Level Security enabled**, no anon policies (all access is via the server-only Drizzle client over the Supabase pooler in this feature; D3).

> Schema is defined as code in `lib/db/schema.ts`; the SQL migration is generated by
> `drizzle-kit generate` into `drizzle/`. Column names are snake_case in Postgres, mapped to
> camelCase TypeScript properties by the Drizzle schema.

## Value object: PaymentStatus

Controlled vocabulary — single source mirrored in DB CHECK, Zod enum, and TS union.

| Value | Meaning |
|-------|---------|
| `pending` | Initiated, unconfirmed (initial state on creation). |
| `success` | Payment completed. |
| `failed` | Payment failed or was canceled. |
| `refunded` | Previously successful, then reversed at the provider (excluded from net revenue, SC-006). |

> "Fulfilled" is **not** a payment status — it is the `fulfilled` boolean on a `success` order.

### Allowed status transitions

Enforced by the DAL's status-update guard (unit-tested):

```text
pending  → success | failed
failed   → pending | success   (retry: reuse the same order, FR-007a)
success  → refunded
refunded → (terminal)
```

- `pending → pending` and idempotent re-application of the current state are no-ops (safe
  under duplicate webhooks, US3 / SC-003).
- Any transition not listed above is rejected.
- Marking `fulfilled = true` is only permitted while `payment_status = 'success'` (independent
  of the transition table).

## Lifecycle

```text
create (pending, not fulfilled)
   │
   ├─ attach payment reference ──▶ pending (stripe_payment_intent_id set)
   │
   ├─ provider confirms ─────────▶ success
   │        │
   │        └─ business fulfills ─▶ success + fulfilled=true   ("Fulfilled")
   │        └─ later reversal ────▶ refunded
   │
   └─ provider reports failure ──▶ failed
            └─ customer retries ──▶ (same row) pending → success/failed   (FR-007a)
```

## Derived / reporting semantics (for later specs, defined here for consistency)

- **Net revenue** = Σ `amount` where `payment_status = 'success'` − Σ `amount` where
  `payment_status = 'refunded'` (SC-006).
- **One record per purchase** holds across retries because retry updates the existing row
  rather than inserting (FR-007a, D7).
