# Implementation Plan: Data & Payment Foundation

**Branch**: `001-data-payment-foundation` | **Date**: 2026-07-31 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/001-data-payment-foundation/spec.md`

## Summary

Establish the order **record of truth** and the shared server-side data foundations every
later feature depends on: a PostgreSQL `orders` table (managed via Supabase), a locked
payment-status vocabulary (`pending / success / failed / refunded`) with fulfillment tracked
as a separate boolean, and a `server-only` Data Access Layer (DAL) that is the sole holder
of database credentials and the sole path through which orders are created, read, and
transitioned. Idempotency (one record per payment / per purchase, including retries) is
enforced at the data layer via a partial unique index on the payment reference plus
upsert-by-reference semantics. No UI, no payment-provider integration, and no webhooks are
in scope — this feature only lays the data + validation seam those features build on.

## Technical Context

**Language/Version**: TypeScript 5.x (strict); Node.js ≥ 20.9 (required by Next 16)
**Primary Dependencies**: Next.js **16.2.12** (App Router, Turbopack default), React 19.2.4;
to be added — `drizzle-orm` + `postgres` (postgres.js driver) for typed DB access,
`drizzle-kit` (dev) for migrations, `zod` (validation), `server-only` (client-import guard)
**Storage**: Supabase (PostgreSQL) accessed via **Drizzle ORM**. `orders` table is the system
of record, defined as schema-as-code in `lib/db/schema.ts`; SQL migrations are generated by
`drizzle-kit` into `drizzle/`. Serverless connections use the Supabase transaction pooler
(port 6543) via a single `DATABASE_URL`, postgres.js with `{ prepare: false }`.
**Testing**: Vitest for unit (schema/domain/status-transition logic) + integration tests
against a Supabase test/local database. (Test runner to be added; no runner is installed
yet.)
**Target Platform**: Vercel (serverless / Node runtime) + Supabase Cloud
**Project Type**: Web application (Next.js App Router) — this feature contributes only
server-side `lib/` + `features/` modules and a DB migration; no routes or pages.
**Performance Goals**: Single-order lookups by id or payment reference resolve in a single
indexed query; the foundation itself carries no throughput target beyond correctness (single
low-volume product store).
**Constraints**: Database credentials MUST never reach the client — all secrets/important
values live ONLY in `.env.local` (gitignored) and MUST NOT carry the `NEXT_PUBLIC_` prefix
(that prefix inlines a value into the browser bundle). `lib/db` (which reads+validates
`DATABASE_URL` and builds the Drizzle client) is `server-only`, and the DAL is the only path
to order data. A committed
`.env.example` documents the required vars with placeholder values only. All external input
validated with Zod before it touches the DB. Amounts stored as integer minor units (no floats).
**Scale/Scope**: One product, low order volume. Schema designed to evolve (per spec Note).

**Stack-version note**: The constitution states "Next.js 15", but the repository is on
**Next.js 16.2.12 / React 19.2**. This plan targets the installed version. Recommend a PATCH
amendment to the constitution's Technology Constraints to say "Next.js 16 (App Router)".
Practical v16 implications honored here: `server-only` DAL and direct `process.env` access
(runtime-config APIs were removed in v16); async request APIs are irrelevant to this
server-only data layer.

**Structure Decision**: Web application (Next.js App Router). This feature adds only
server-side modules and Drizzle-generated migrations. Shared infrastructure (env access,
Drizzle client + schema) lives in `lib/` per the constitution; the order domain is a
self-contained feature module in `features/orders/` (domain / types / schemas / data) with a
single `index.ts` public surface. The DAL (`order.repository.ts`) and `lib/db`
carry `import 'server-only'` so a build error fires if any client module imports them.
